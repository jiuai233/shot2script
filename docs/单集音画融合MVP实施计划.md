## 1. 首轮范围与固定配置

- 输入：`videos/sample/E01.mp4`，时长约 90.28 秒，文件约 13 MB。通过原生视频接口整集传入，Base64 大小低于接口 50 MB 上限。
- 输出：隔离运行目录中的 Markdown 工作稿、核对结果、人物归属及阶段记录。生产入口、模型配置、原有剧目数据保持原状。
- 服务：`https://token-plan-cn.xiaomimimo.com/v1`；密钥读取项目 `.env` 的 `MIMO_API_KEY`，不写入记录。
- 模型：转写使用 `mimo-v2.5-asr`，每次最多输出 4096 token；读视频的视频理解使用 `mimo-v2.6-pro`，不显式指定推理开关或等级，每次最多输出 16384 token；融合写稿与文稿检查只处理文本，使用 `deepseek-flash`，开启思考、强度 `high`，每次最多输出 32768 token。
- 视频理解使用原始整集视频及原声，`fps=2`、`media_resolution=default`。音频处理保留原始混合声音，统一为 16 kHz、单声道 PCM WAV，沿用现有提取函数保持时间原点。

### 视频采样边界

源视频保留原始 30 fps，不预先降帧或重编码。`fps=2` 设置在原生视频请求项中，表示服务端读取时的采样频率；入口直接读取 MP4，已有帧图片及送图筛选配置不参与该接口输入。实际采样帧数和最终缩放分辨率未返回时保留未知，不以时长乘以 2 充当实测值。

首轮固定使用每秒 2 帧；后续采样调整以完整实跑发现的漏动作及实际用量为依据。

正常完成一次整集共 **4 次远程请求**：ASR、视频理解、融合写稿、文稿检查各一次；只有视频理解上传视频。本地对齐、人声检测与切句不产生远程请求。

## 2. 运行顺序：两路并行，汇合后串行

**图 2.1：融合写稿必须等待语音、视觉两路均完成。** 箭头表示执行依赖，分叉表示并行，汇合表示等待全部前置结果。

```text
① 固定准备：检查输入、建立独立目录、提取时间对齐的音轨
                         │
              ┌──────────┴──────────┐
              │                     │
       ②A 语音支路              ②B 视频支路
       MiMo ASR 转写            Pro 整集视频理解
              ↓                     ↓
       指定文本强制对齐          人物、动作、对白归属候选
              ↓                     │
       VAD 人声检测、按词切句      │
              │                     │
              └──────────┬──────────┘
                         ↓ 等待两路完成
                   ③ DeepSeek 融合写稿
                         ↓
                   固定数据检查
                         ↓
                   ④ DeepSeek 文稿检查
                         ↓
                   ⑤ 保存文稿与核对结果
```

### 并行边界

1. **语音支路和视频支路并行**：固定准备完成后同时启动。视频理解直接接收原视频，不等待 ASR，不读取语音支路的结果。
2. **语音支路内部串行**：ASR 文本先交给对齐器，真实词时间用于切句。VAD 使用现有固定处理流程。
3. **汇合后串行**：融合写稿等待两路结果；固定检查等待工作稿；文稿检查等待固定检查结束；最终结论等待文稿检查结果。

本轮只建立上述两路并发，不增加其他并发调度层。

## 3. 各阶段的数据与职责

### ②A 语音支路：台词与真实时间

输入为固定流程提取的整集 WAV。

1. 调用 MiMo ASR，保存原始响应与转写文本；设置 `asr_options.language=zh`。
2. 单独加载本地 `models/asr/qwen3-aligner-0.6b`，调用现有 SDK 的 `aligner.generate(audio_path, text=转写文本, language="Chinese")`，得到真实词时间。复用 `restore_punctuation()` 与 `coalesce_zero_spans()`；本阶段只加载对齐模型。
3. 复用 `s2s.vad.detect()`、`waveform()` 和 `s2s.asr.single.segment()`；显式使用 `min_pause=0.3`、`max_sentence=6`。句编号沿用 `E01-S001` 格式，保存疑似漏段和句内异常。
语音结果包含：ASR 全文、词时间、句编号与起止、每句原文、句内异常、疑似漏段及待核对问题。语音支路不判断说话人；人物由融合写稿根据画面与台词文字判断。

### ②B 视频支路：人物与可见事实候选

一次请求接收整集原生视频，输出：

- **人物**：临时编号、具体外观、出现时间及跨镜头对应候选。
- **动作**：执行者、对象、可见行为、时间范围和依据；保留存疑项。
- **对白归属候选**：听到的短句、候选说话人、画内／画外／设备声音形态、声音表现（音量、语速、哭腔、发颤等）、说话人可见神态及依据；无明显表现时为空。
- **待核对**：人物连续性、局部身体归属、遮挡、重叠等具体缺口。

视频模型返回的时间只作为粗定位，不覆盖对齐器产生的词时间。字幕仅作参考，不能直接把对白称呼转为已确认人物身份。

### ③ 融合写稿：先统一人物，再组织正文

一次独立 DeepSeek 请求接收逐句语音摘要、视频观察和一份自包含的融合提示词，在同一返回中输出人物映射、逐句归属、动作采用记录、工作稿及未决问题。语音摘要保留句编号、原文、起止、异常、疑似漏段和未决问题；不附全文副本或词时间。完整对齐结果保存在本地，固定检查继续使用原始记录。写稿规则集中于 `prompts/mvp/融合写稿.md`。

1. **统一人物**：先建立本集统一编号和唯一显示名称，记录名称类型、命名依据、外观、别称、视觉临时人物。沿用已确认登记名；允许有依据且唯一指向人物的关系称谓，只有外观依据时使用具体外观描述名。称呼者、被称呼者及回应等关系依据单独记录，不凭单次称呼补造身份。同一视觉人物不得映射到多个统一人物。
2. **逐句归属**：逐句综合真实时间、语音异常和画面依据。不能因为当前画面出现某人，就把电话另一端或画外对白归给该人物。
3. **组织动作与对白**：按真实时序形成分场剧本；说话人的简短相关动作及有依据的声音表现、神态放在括号中，括号不超过 12 字，其他动作使用 `△`。保留有依据的对象、互动和结果，不把台词内容写成已发生的画面动作。
4. **登记未决**：句内混人、身份或动作未定时登记未决问题，正文不写待核对标记；说话人拿不准时写最可能的人物。保留原台词及关键事件。首轮不让模型自行改造词时间或句界。

工作稿使用 PRD 的场景、人物行、对白与动作格式。对白行和采用动作所在行以行首编号标记（如 `〔E01-S001〕`、`〔A001〕`）关联原句和动作，固定程序据此计算逐句归属与采用动作的正文行号，并在渲染前去掉标记；标记引用未登记编号、同一编号标在多行或原句缺少标记时列入固定检查问题。未确认内容登记在未决问题中，位置写句、动作或人物编号；渲染时清除正文残留的待核对标记。模型返回模板，人物行、对白标签、△ 及动作括号中的人物引用 `{{P001}}` 等统一编号，由固定程序渲染为登记显示名；渲染保持行数及对白原文不变。照录的画面字卡不做替换，内部编号不进入最终正文。

固定检查覆盖以下问题：

- 所有原句按序覆盖一次，原文一致，不能漏句、重复或静默改字。
- 人物引用存在，未知用 JSON `null`，不能输出字符串 `"null"`；人物行、对白标签、△ 和动作括号不混用别称或已登记的旧外观名。同一视觉人物重复映射须列问题。
- 对齐时间、句引用及采用动作的时间范围有效，不超出整集边界。
- 说话人括号超过 12 字时列入问题清单，提示改写 △。

固定检查发现内容差异时，保留工作稿，继续文稿检查，并将差异并入最终结论，不静默修正文稿。只有结果结构损坏、无法获得完整工作稿时才停止依赖阶段；不追加模型请求补写。

### ④ 文稿检查：只看文本找离谱问题

一次 DeepSeek 请求，输入带行号工作稿、台词原文与时间、人物名称及别称，不提供视频、视觉识别记录或写稿推理。台词逐字、顺序、行号和人名统一由固定检查负责，文稿检查不重复。规则见 `prompts/mvp/文稿检查.md`，问题分两级：

- 阻断：对白明显归错人（自问自答、电话或画外另一端归给接听者、称呼矛盾、对答接不上）；无依据的关键事件或人物关系；缺场景行、人物行或本场说话人，读不出谁在场。括号中的声音表现与神态来自素材，不按无据情绪处理；拿不准时不判阻断。
- 规范：非对白代词或泛称、心理描写、无据情绪、文学修饰、镜头语言、括号与 △ 用法、动作重复或提前。

最终结论由程序给出：固定检查中的台词改字、漏句、乱序、无原句的对白行，以及文稿检查的阻断问题，判“不通过”；其余固定检查、文稿检查规范问题、融合未决、视频与语音待核对、人物映射待核对列入问题清单，判“通过（附问题清单）”；没有任何问题判“通过”。

## 5. 实跑命令与交付标准

从项目根目录执行；`.env` 须包含 `MIMO_API_KEY` 与 `DEEPSEEK_API_KEY`，本地环境与模型须存在。远程调用失败保留阶段结果，不自动重试。除 ASR 外的请求均为流式，60 秒未收到新数据或总计 600 秒即停止，推理过程保存在阶段产物。E01 已出现原生视频审核拒绝，尚未完成真实整集验证。

```bash
.venv/bin/python -m pytest -q tests/test_mimo_mvp.py

.venv/bin/python tools/run_mimo_mvp.py \
  videos/sample/E01.mp4 \
  --输出 "tmp/experiments/MiMo-MVP/E01-$(TZ=Asia/Shanghai date +%Y%m%d-%H%M%S)"
```

输出目录须为新的运行目录。交付物为：

1. `工作稿.md`：完整单集可审阅稿，未决归属和事实明确标记。
2. `核对结果.json`：结论（通过、通过（附问题清单）、不通过）、阻断问题与问题清单，每项注明来源。
3. `人物归属.json`：统一人物、视觉临时人物映射、逐句归属、动作与正文对照。
4. `运行记录.json`：阶段状态、开始／结束时间（UTC+8）、耗时、实际模型、参数、HTTP 状态、`finish_reason` 与原始 `usage`。
5. `阶段产物/`：音轨、ASR 原始响应、对齐、VAD 与切句结果，以及视频理解、融合写稿、文稿检查的原始响应与推理过程。

### 完成标准

- 输入只有本轮指定视频和明确的配置，不将评测标注或旧人工归属作为隐藏答案送入模型。
- 两路真实处理完成，融合写稿和文稿检查均执行，文稿覆盖完整台词，并附人物归属与可定位的问题。
- 人物统一、电话错归、抓肩等关键互动和掉落物辨识接受原素材检查；原有人工标注只作辅助参考，不据未完成校对的标注报告完整准确率。
- `流程状态` 和 `内容结论` 分开记录。内容结论取通过、通过（附问题清单）或不通过，不产生生产正式发布状态。

## 6. 实际阻塞的处理

- 原生视频曾出现 `content_filter`，具体触发原因未知。任何阶段遇到审核拒绝、鉴权失败、超时或无法解析的结果，保留原响应及已完成产物，停止依赖该结果的阶段，记录流程中断；不冒充整集跑通。
- 每个远程请求连接超时 15 秒、读取超时 180 秒，不自动重试或追加格式重答。调用记录以实际发生为准。
- Token Plan 的接口 `usage` 与套餐实际扣额分别对待；未返回的用量保留 `null`。首轮不把 token 换算成已扣人民币金额。
- 本轮输出为隔离实验工作稿及核对结果，生产配置和生产正式发布规则保持原状。
